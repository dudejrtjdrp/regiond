# AI 활용 기술 문서 — 갈래말래 (가제)

최종 수정: 2026-08-06 (AI 자동 최신화 — §17-19 표현·타격감/대화창까지 반영)

## 1. 개발 공정에서의 AI 활용

### 1-1. 역할 분담 파이프라인
```
이성효 (기획서 v6.0 + 유물 문서 → GDD v3 지시, Notion)
  └→ Claude Fable 5  : 기획 통합 분석 → 모순 발견·구현 결정(D1~D12) → SPEC.md + PROTOCOL.md 작성
        ├→ Opus 에이전트 A (서버) ─┐  프로토콜 계약만 공유하고 완전 병렬 개발
        ├→ Opus 에이전트 B (클라) ─┘
        └→ Opus 에이전트 C (통합·QA) : 쟁점 해소, E2E, 밸런스 튜닝, 실브라우저 스모크
```
- **계약 우선 병렬화**: 서버·클라가 서로의 코드를 모르는 채 PROTOCOL.md만 보고 동시 개발 → 통합 에이전트가 쟁점을 일괄 해소. 에이전트 3기 병렬+직렬 조합
- **검증 강제**: 각 에이전트에 "밸런스 문서의 표 값을 테스트로 재현하라"를 요구 — 기획서 수치(드래곤 R=1.14→66%, 무역 배수 1.17/1.46/2.25 등)가 **테스트 123개**로 고정됨
- **모순 검출**: AI가 기획서 간 수학적 충돌 4건(시간 모델, 연료 소비, 감정의 날 조건, 평시 방어 노동)을 계산으로 발견 → QUESTIONS.md로 기획자에게 회부
- **계약 불일치 검출(v3.0 QA)**: 자료 파일끼리의 어긋남도 테스트로 못 박았다 —
  `skills.defs[*].nodeTypes` 에 있는데 `skills.nodes` 에 규격이 없던 `water`(물가)가 그렇게 잡혔고,
  이제 `test/fishing.test.js` 가 "스킬이 맡는 노드는 전부 스윙 규격이 있다"를 매번 검사한다

### 1-3. AI 가 스스로 잡은 사고 (v3.0 QA 세션)
사람이 리포트하지 않았는데 **검증 도구가 먼저 찾아낸** 것들이다 — 도구를 정확하게 만드는 일 자체가 AI 활용의 핵심이었다.

| 사고 | 어떻게 드러났나 | 정공 해법 |
|---|---|---|
| 도끼질을 해도 자원칸이 최대 10분 묵는다 | 안개 수정으로 `lordMove` 의 상태 전량 방송을 걷어내자 곧바로 하니스가 실패 — **우연히 가려져 있던 사고**였다 | 실시간 ack 에 창고 잔고(권위값)를 실어 화면 장부에 즉시 반영 |
| 토스트가 컷신 [건너뛰기] 단추를 덮어 못 누른다 | 실브라우저 스모크의 **진짜 마우스 클릭**이 안 먹혀서 `elementFromPoint` 로 추적 | 시간이 정해진 단추를 알림 위로 + 컷신 중 알림 더미를 비켜 세움 |
| 성능 게이트가 통과 불가능한 조건이었다 | 「평균 프레임 시간 < 16ms」가 늘 16.67ms — 재는 값이 **프레임 간격**이었다 | 그리는 데 든 시간(0.27ms)과 간격(16.67ms)을 나눠 재도록 지표 재정의 |
| 하니스·스모크가 매번 다른 땅을 받아 간헐 실패 | 물가가 없는 지도·울타리 자리가 물인 지도에서만 실패 | `?seed=` 손잡이를 두고 검사에서 **씨앗 고정** |

### 1-4. 세션 인수인계 파이프라인 (2026-08-06~, 계정 이전 후)

- 배치 C(§17-18): 「감정의 날에 감정되는 요소가 너무 적다」는 피드백에 대해 Opus 에이전트가 **먼저 태그 효과 키의 소비처를 전수 grep** 해 `output`·`gather` 둘만 살아 있고 `defenseTotal`·`populationGrowth`·`unlock` 은 아무도 읽지 않는 죽은 키임을 확인한 뒤, 살아 있는 키 안에서만 새 태그 2종을 설계. 전 태그에 한 줄 이야기(flavor)를 붙이고 컷신을 「5 + 태그 수 + 1」장으로 늘림. 테스트 352/352

- 배치 D(§17-19): 「표현·타격감」은 수치로 못 박기 어려운 영역이라 **에이전트에게 자료 다이얼부터 만들게 했다** — 흔들림 세기·붉은 섬광 농도·스프라이트 배율·타자 속도까지 전부 `data/world.json render.*` 로 빼고 코드에는 한 숫자도 남기지 않았다(「손맛이 약하다」는 피드백이 오면 코드가 아니라 표 한 줄을 만진다). 착수 전 감사에서 **건물 확대의 진짜 위험**을 먼저 찾아냈다: 그림(`world.drawStructures`)과 클릭 판정(`input.structureAtSprite`)이 같은 사각형 식을 각자 베껴 쓰고 있어, 키우는 순간 「보이는데 눌러지지 않는 건물」이 생긴다 → 식을 `world.structureRect` 한 곳으로 합치고 그 동치성을 테스트로 못 박은 뒤에 확대했다. 대화창(D-5)은 외부 그림 파일 없이 atlas 절차 도트를 키워 초상으로 썼다(에셋 0장 원칙 유지). 회귀는 「눈으로 봐야 아는 것」을 뺀 나머지 — 사각형 동치·대화창 규칙 9종을 새로 붙였다

신규 21종 중 **열셋이 여전히 갈 길이 없었다** — 저쪽이 연 것은 `temple` 계열뿐이었다. 이 배치(R4d)는
정확히 그 열셋의 길을 낸다: 사슬 결말 11자리(얼어붙은 원정대 → 나침반·곡괭이·일지 / 지도 조각 →
얼어붙은 왕의 홀 / 덩굴 사원 → 세계수의 씨앗 / 낯선 발자국의 은둔자 → 사냥꾼의 맹세 / 버려진 깃발의
저주받은 땅 → 굶주린 왕관 …), 카드별 풀(봉분의 금기 → `ruin:barrow`, 제단의 이름 부르기 → `ruin:altar`),
땅의 변주(설산 유적 → 「얼음 밑 돌무지」 → `ruin:snow`), 국가 이벤트 보상(에르니아 왕위 계승의 조약에
**응한** 나라 → 기관장의 인장). 회귀 테스트가 「갈 길 없는 유물」을 전수로 세고, 지금 그 목록은 비어 있다.

**결정론에서 실제로 사고를 낼 뻔한 자리.** 설산 변주를 처음에 `biomeCardFor(...) ?? rng.pick(cards)`
로 썼다. 단락 평가 때문에 변주가 있을 때 **난수를 한 톨 덜 쓴다** — 설산 유적을 한 번 연 판은 그 뒤
모든 굴림이 밀린다. 「같은 씨앗의 두 rng 가 같은 만큼 소비했는가」를 묻는 회귀가 이것을 잡았고,
뽑기는 언제나 하고 **뽑은 뒤에 덮어쓰는** 꼴로 고쳤다. 같은 결로 카드 배열은 12장 붙박이이고,
새 선택지는 반드시 `leave` **앞에** 끼웠다(시뮬 봇이 늘 `reject` 를 보내고 엔진이 마지막 옵션으로

`micro:jungle`(아쿠아의 물방울)을 `chain:jungle` 로 옮겼다 — 항목 하나가 모든 링의 미시 발견 자리를 민다.

**좁은 풀에서도 등급표를 살렸다.** 공용 문 `grantVia` 는 후보가 있는 등급만 남겨 **등급표를 다시

## 부록 — 재시작마다 서버가 죽던 버그: 세이브에 굳은 캐시 (2026-08-09, opus 세션)

**증상.** `npm start` 하면 배너 세 줄을 찍고 곧장 죽었다.
`TypeError: overlaySet(...).has is not a function` — companions.walkable → onBridge 의 첫 걸음이다.
「자꾸 튕긴다」의 정체는 서버 프로세스가 통째로 내려간 것이지 클라이언트 문제가 아니었다.

**진짜 원인은 자료형이 아니라 자리다.** `Set` 은 `JSON.stringify` 를 지나면 `{}` 가 된다.
research.js 는 칸 집합 캐시(`_bridgeSet`·`_fillSet`·`_railSet`)를 **나라 객체에 얹어** 두었고,
나라는 그대로 snapshot.json 에 실린다. 그래서 저장 파일에는 `"_bridgeSet":{}` 가 굳었다
(실제로 saves/ 안 스냅샷 30여 개 전부에 들어 있었다). 되읽으면 캐시 유효성 검사가
`if (!nation._bridgeSet || nation._bridgeStamp !== list.length)` — 빈 객체는 **truthy** 이고
스탬프(숫자)는 JSON 을 멀쩡히 건너오므로 「유효한 캐시」로 통과한다. 그리고 `.has` 가 없다.
세이브를 물고 뜨는 서버는 **매번 같은 자리에서 죽는다** — 다리 하나 없어도(길이 0 = 스탬프 0) 죽는다.

**고친 방식은 프로젝트에 이미 있던 규율을 따랐다.** spatial.js 규율 ①(「파생 캐시는 저장하지 않는다」)과
fog.js 의 `RATIO_CACHE` 가 같은 답을 이미 적어 두었다 — **WeakMap 에 매단다**. research.js 에
`TILE_SETS`(WeakMap<nation, Map<'rails'|'bridges'|'fills', {set,len}>>) 하나를 두고 railSet·overlaySet 을
그 위로 옮겼다. 일 틱의 structuredClone 이 새 나라를 만들면 캐시도 저절로 새로 나고, 스냅샷에는
한 바이트도 실리지 않는다. `_bridgeSet` 류 여섯 낱말은 OVERLAYS 표에서 지웠고, 옛 세이브에 남은
찌꺼기는 persistence.unpackFog 이 읽는 자리에서 털어 낸다.

**두 번째 고침 — 시계 하나가 죽어도 서버는 안 죽는다.** `setInterval` 콜백에서 새는 예외는 잡아 줄
프레임이 없어 프로세스를 그대로 내린다. 일 틱·생태·전투 세 타이머를 `safeBeat(이름, fn)` 로 감쌌다:
한 박자를 건너뛰되 5초에 한 번은 반드시 콘솔에 찍는다(조용히 삼키면 그게 다음 버그다).
이 방어가 있었다면 이번 버그는 「서버가 안 뜬다」가 아니라 「로그가 시끄럽다」로 나타났을 것이다.

**회귀.** `test/playtest21a4_tilecache.test.js` 3건. ① 저장 왕복(JSON.stringify → parse) 뒤에도
onBridge/onFill/onRail 이 답한다 ② 스냅샷 JSON 에 캐시 낱말이 한 글자도 없다 ③ 옛 세이브의
`_bridgeSet: {}` 를 읽어도 무사하다 ④ 지우고 같은 수만큼 다시 놓아도 답이 낡지 않는다.
**고치기 전 코드로 돌려 ①②③이 실제로 빨갛게 뜨는 것을 확인**하고 커밋했다(③은 옛 코드에서 그

## §22. 유적 개편 — 「도달 불가능한 콘텐츠」를 AI 가 먼저 찾아낸 사례 (2026-08-09)

**사람이 준 것은 증상 한 줄이었다.**

> "유적 살피기가 뭘 하는지 전혀 감도 안 오고 왜 있는지도 모르겠어. 세 번 두드리면 옛 자취 뜨는데
> 한 번 캐면 그만이 아니라 계속 뜨고 있고. 뭘 위해 있는 거지?"

**AI 가 한 일은 「재미없다」를 코드 경로로 번역한 것이다.** 밸런스를 만지거나 카드를 더 쓰기 전에
유적이 지나는 길을 전수 추적했더니, 재미의 문제가 아니라 **연결의 문제**였다:

게이지를 소비하고 카드를 뽑는 코드가 오직 `apAction {type:'explore'}`(왕의 행동력 행동) 안에만
있었는데, 클라이언트에서 `apAction` 을 보내는 곳이 **0곳**이었다(`net.js` 허용 목록에 이름만 남아
있었다). 즉 `data/ruins.json` 의 카드 12장, `temple.js` 의 신전 3단 사슬, 크기별 등급 보정이
**통째로 도달 불가능한 콘텐츠**였다. 화면에 뜨던 `옛 자취 4/3` 은 나라 누적 게이지라 분모가 이
자리의 것도 아니었고, 넘어도 아무 일이 없었다. 유저가 본 것은 정확히 그것이었다.

**그 다음이 더 중요했다 — 버그를 고쳐도 남을 설계 결함을 갈라 적었다.**

| 유저가 말한 것 | AI 가 짚은 원인 | 버그인가 설계인가 |
|---|---|---|
| 보상이 안 온다 | `apAction` 호출부 0곳 | 버그 |
| 뭘 하는 건지 안 보인다 | 게이지가 **국가 누적**이라 이 자리에 끝이 없다 | 설계 |
| 왜 찾아가야 하는지 모르겠다 | 크기가 스윙 수만 늘려 「같은 일을 다섯 배 오래」였다 | 설계 |

버그만 고쳤으면 카드는 떴겠지만 「지금 두드린 이 자취가 카드를 준 것이 아니다」는 그대로 남는다.
그래서 나라의 저금통을 없애고 **노드가 진행을 쥐게** 했다(`rooms`·`roomsOpened`·`spent`).
크기 1~4는 이제 인내력이 아니라 **방의 수**이고, 4~6 스윙마다 카드가 한 장씩 선다.

**구현 단계에서 AI 가 스스로 잡은 것 셋** — 설계 문서를 쓸 때는 안 보이던 것들이다.

| 사고 | 어떻게 드러났나 | 해법 |
|---|---|---|
| 결정 열쇠 충돌 | 옛 `decisionId` 는 `ruin_<나라>_<틱>_<카드>` 인데, 방 사이가 4~6 스윙이라 **같은 틱에 방 둘을 여는 일이 흔하다** — 하나가 조용히 삼켜진다 | 열쇠에 노드 id·방 번호를 넣고 회귀로 못 박음 |
| ack 의 진행 수가 규격이었다 | `swingsPerCycle` 을 `spec.swings`(규격)로 실어 보내고 있었다. 유적만 노드 값(4~6)이 규격(4)과 달라 **화면 진행바가 유적에서만 어긋났다** | ack 이 그 노드의 값을 싣도록 수정 |
| 깊이 보정 표의 인덱싱 | `roomBoostCurve` 를 방 번호로 직접 읽으면 방이 둘인 자취의 끝 방이 0.5 를 받아 「끝까지 갔는데 덜 준다」가 된다 | 깊이를 0~1 로 정규화해 읽고, 그 경계를 회귀 한 건으로 고정 |

**결정론 규율을 새 경로에도 그대로 적용했다.** 구 경로는 왕의 행동력이 쥔 **월드 난수**로 카드를
뽑았는데, 스윙은 실시간 명령이라 그대로 옮기면 웨이브 구성·사건·이름이 통째로 밀린다(§13-C 에서
겪은 사고다). 궤(`openCache`)가 이미 쓰던 답을 그대로 따라 `statRng('<씨앗>:ruin:<노드id>:<방번호>')`
로 지었고, 덤으로 「같은 지도의 같은 방은 언제 열어도 같은 카드」가 공짜로 따라왔다.

**재활용 우선 원칙.** 새로 지은 것은 방 개폐 로직 하나뿐이다. 카드 12장 · 결정 큐와 `decide` 규약 ·
`ruinEvent` · 결정 UI · `statRng` · 유물 지급(`grantVia`/`dropPool`) · 신전 3단은 **전부 있던 것을
그대로 썼다** — 여태 문이 잠겨 있었을 뿐이다.

**회귀.** `test/playtest22_ruinrooms.test.js` 11건 신규(그 자리에서 열림 · 나라 게이지 부재 ·
폐허로 남되 재타격 거부 · 깊이 보정 · 열쇠 충돌 · 결정론 · 죽은 명령 제거 · 자료 온전성 2건).
