# QUESTIONS — 성효가 확인해줘야 하는 것들

> 구현은 멈추지 않고 전부 끝냈다. 아래는 **내가(AI) 임의로 정하고 진행한 것들**이라, 네 확인이 필요하다.
> 각 항목의 [현재 상태]대로 이미 동작한다. 바꾸려면 대부분 `data/*.json` 다이얼 수정만으로 된다.

## ★ 최우선 — 게임의 방향이 걸린 결정 5개

- [ ] **1. 시간 모델 (가장 중요).** 기획 전반부(1틱=실시간 10분, 시즌=실시간 14일≈게임 5.5년)와 밸런스 문서(day5/9/13 침공, 14일 누적 계산)가 수학적으로 양립 불가였다. **밸런스 문서를 살려서 "1틱=게임 1일, 시즌=14틱"으로 구현**했고, 틱당 실시간 길이는 다이얼이다(데모 30초 → 시즌 7분 / 10분으로 놓으면 시즌 ≈ 실시간 2.3시간). 원안처럼 "실시간 14일 지속형"으로 가려면 게임일수를 늘리거나 하루를 여러 틱으로 쪼개고 밸런스 전면 재검증이 필요하다. → 시즌 실플레이 길이를 얼마로 잡을까?
- [ ] **2. 게임 제목.** 미정이라 코드네임 "Regiond" 그대로 썼다 (폴더명 gallaemallae). 제목 정해지면 알려달라 — UI 문자열은 한 곳(index.html + 템플릿)에 모여 있다.
- [ ] **3. 해적 공격력 150→140.** 시뮬 200회에서 해적 승률이 57.5%로 목표(60~70%) 미달 — 원인은 성지 T1 완공 전 하루는 인구 50이라 §6-4 표의 전제(인구 90)가 안 맞아서다. 다이얼만 140으로 내려 65.8%로 맞췄다. 기획 검증표(§6-4) 원본은 150 그대로 보존. 승인?
- [ ] **4. 아트 톤.** §19 미결정("양피지 vs 밝은 도형"). 현재는 **다크 판타지 + 절차적 도트**(이미지 에셋 파일 0개, 전부 캔버스/CSS 생성)로 만들었다. 실제 도트 에셋을 그려 넣을지, 지금 톤으로 갈지.
- [ ] **5. 멀티 범위.** §19 미결정(PvP vs 협력). **한 국가 1~5인 협동**(socket.io, 중도 합류 시 NPC 대체)으로 구현했다. 국가 간 대전·방해는 범위 외. 이대로 갈까?

## E. 오픈월드 규칙 — 기획 판단이 필요한 것

- [ ] **E-1 노드 고갈이 산출에 미치는 영향이 이게 맞나.**
  [현재] 숲(회복 7 / 인당 소모 1.2)·바위(4 / 0.9)는 **회복이 소모보다 훨씬 커서 사실상 안 마른다** — 다섯 무리를 붙여도 늘어난다.
  실제로 마르는 건 회복 0 인 **철광맥·유막**이고, 그건 `flatYield`(철광 2 / 원유 1)가 끊기니 진짜 손해다.
  다 캐면 `depleted` 가 되고 **다음 틱에 서버가 백성을 자동으로 다른 자리로 옮긴다**(`reassignDepleted`).
  숲·바위 쪽 고갈은 **노드 기여(최대 +20%)가 잠깐 빠지는 것**이 전부이고 콥더글러스 본 산출은 배치 비율만 보므로 거의 안 떨어진다.
  → ① 숲·바위도 **과채집하면 실제로 마르게** 할까(회복량을 낮춰 '자리를 돌려 쓰는' 압력 만들기),
  아니면 ② 지금처럼 **철광·유막만 유한 자원**으로 둘까?
  (①로 가면 §6-4 검증표·시뮬 체크포인트를 다시 잡아야 한다)
- [ ] **E-2 배치 인접 보너스를 어디까지 넓힐까.**
  [현재] 6종만 붙는다 — 곡창↔밭/기름진 땅, 창고↔밭·기름진 땅·숲, 병영↔바위, 도로·영사관↔물, 성지↔유적.
  반경 5칸, 노드 1곳당 +2%, 상한 +10%, **건축가 재임 + 왕이 손수 좌표를 찍은 건물**일 때만.
  → 공방·성벽 같은 나머지 건물에도 짝을 만들어 줄까? 상한 10%가 "자리를 고민할 값어치"로 충분한가?
  (이 보너스는 AP 와 같은 '접속한 사람만 얻는 보너스'라 시뮬 체크포인트는 이것 **없이** 성립한다 — 넓혀도 밸런스는 안 깨진다)
- [ ] **E-3 해적전에 터렛이 한 기도 안 선다(평균 0.00기).**
  [현재] 5일차 해적은 성벽 티어가 낮아 자리(T0=2기)가 거의 없고, 봇은 다음 건물 자재를 먼저 지키느라 못 산다.
  그래서 **첫 침공은 타워디펜스가 아예 등장하지 않는다** — 리플레이도 빈 타임라인이다.
  → 첫 침공부터 터렛 맛을 보여 주려면 ① 성벽 T0 자리를 2→3 으로 늘리거나 ② 화살탑을 더 싸게 하거나
  ③ 튜토리얼로 화살탑 1기를 공짜로 주는 방법이 있다. 어느 쪽? (①②는 해적 공격력 재조정이 따라온다)
- [ ] **E-4 화포의 원유 3이 사실상 봉인 조건이다.**
  [현재] 화포는 강재40 + **원유3** + 80G 이고, 원유는 유전 태그국과의 무역 사슬이 있어야 들어온다.
  바이킹(=화포 상성)전 시점에 원유를 3 이상 쥐고 있는 판이 흔치 않아, 상성 터렛이 **가장 필요한 순간에 못 세워진다**.
  → 의도된 "무역 사슬 보상"인가, 아니면 원유 2 로 낮추거나 강재로 대체 가능하게 할까?

## F. 멀티·채팅 — 범위 결정

- [ ] **F-1 채팅 스팸을 서버가 막아야 하나.**
  [현재] 서버는 **새니타이즈(제어문자·꺾쇠·공백 압축)와 160자 길이 제한, 최근 100건 링버퍼**만 건다.
  `config.world.chat.cooldownMs`(400ms)는 **설정표로 내보내기만 하고 서버가 강제하지 않는다** — 지금은 클라 예의다.
  즉 스크립트로 초당 수백 줄을 밀어 넣을 수 있다(상태에는 영향이 없지만 방 전체 대역폭은 먹는다).
  → 서버에서 쿨다운을 **강제**할까(초과분 조용히 버리기 / `CHAT_COOLDOWN` 에러)? 아니면 협동 전용이라 이대로 둘까?
- [ ] **F-2 멀티 동명이인이 같은 사람으로 취급된다.**
  [현재] `avatarId` 는 클라가 안 보내면 **`playerName` 을 그대로 쓴다**. 그래서 같은 방에 "가온" 이 둘 들어오면
  아바타·명부·자리 소유권이 **하나로 합쳐진다**(나중 사람이 앞사람의 자리·위치를 그대로 물려받는다).
  → 서버가 접속마다 고유 id 를 발급하고 이름은 표시용으로만 쓸까(그러면 **재접속 시 자리 되찾기**를 위해
  클라가 id 를 저장했다 보내야 한다)? 아니면 건국 화면에서 **같은 방 이름 중복을 막을까**?
- [ ] **F-3 대표 유닛 60은 고정값이어야 하나.**
  [현재] 화면에 서는 백성은 **항상 60무리**이고, 인구가 늘면 `peoplePerUnit`(1무리 = 몇 명)이 커진다.
  덕분에 렌더·경로 비용이 인구와 무관하게 일정하고, 배치 눈금은 1/60(≈1.7%)로 고정된다.
  → 후반 인구 260에서 "1무리 = 4~5명"이 체감상 어색하지 않은지, 아니면 인구에 따라 유닛 수를 늘릴지(120까지)?
  (늘리면 배치 파생 `laborAlloc` 의 오차(±0.02)가 줄지만 렌더 부하가 두 배가 된다)

## G. 진행·난이도 — 플레이테스트로 확인할 것

- [ ] **G-1 1막(1~2일) 무역할 구간이 너무 헐렁하지 않나.**
  [현재] 역할 선택이 감정의 날 뒤로 밀리면서, 1막에는 **각료 초상이 전부 잠겨 있고** 국고 바에도 곡물·목재·석재만 보인다.
  할 수 있는 건 백성 배치 · 개간 · 군주가 몸소 일하기뿐이다(의도한 '점진 공개'다).
  → 이틀이 적당한가? 초보가 "지금 뭘 해야 하지"로 멈추면 목표 카드에 한 줄 더 넣을지, 아니면 1막을 하루로 줄일지.

# v3 (엔드리스 정착지 전환) — 서버 구현 중 생긴 미해결 질문

> 2026-08-04 · 서버 담당. GDD3 를 구현하며 **판단이 필요했던 곳**과 **기획 확정이 필요한 곳**을 남긴다.

## Q-v3-1. 웨이브 파워의 '정착지 규모 보정' — 유지할 것인가 (★ 가장 중요)

GDD3 §6 은 `power = base × 1.18ⁿ × 난이도 배수` 로 못 박았다. 그대로 구현해 보니 **인구 0에서 시작하는**
정착지의 성장이 1.18ⁿ 을 압도했다: 웨이브 1~4는 손도 못 대는데 웨이브 5는 100% 방어, 반대로 세게 잡으면
웨이브 1에서 정착지가 무너져 회복하지 못했다(죽음의 나선). 한 상수로는 두 지점을 동시에 만족시킬 수 없다.

그래서 파워에 두 항을 더 곱했다 (`data/waves.json`):
- `settlementScale = (방어지수 / 70)^0.85` (0.5~8) — 방어지수 = 터렛 DPS + 민병 DPS + 울타리 내구×0.02
- `earlyRamp` — 처음 5웨이브에 0.5 → 1.0 로 오르는 배수

**결정 필요**: (a) 이대로 둔다 (b) 규모 보정을 끄고 대신 웨이브 간격을 정착지 티어에 묶는다
(c) 규모 보정을 켜되 exponent 를 더 낮춰(0.6) 후반 압박을 키운다.
현재 값으로 체크포인트 4/4 통과. `waves.settlementScale.enabled=false` 로 언제든 끌 수 있다.

## Q-v3-2. 엔드리스 후반의 '벽' 위치

시뮬 봇(성실한 플레이어 근사) 기준으로 **웨이브 10~12(대략 70~85게임일)** 부터 생존율이 0에 수렴한다.
패배가 관대해서(전멸·게임오버 없음) 계속 플레이는 되지만, 상용 기준으로 "몇 시간짜리 게임인가"는 기획 결정이다.
- 지금: 1게임일 10분 × 85일 ≈ **14시간**이면 벽에 닿는다(방치 포함).
- 늦추려면: `waves.growth` 를 1.18 → 1.14 로 내리거나, 티어 5~6 건물(화포·기념비)의 전투 기여를 키운다.
**결정 필요**: 목표 플레이 길이(첫 벽까지 몇 시간?).

## Q-v3-3. 스킬 최고 레벨(20)까지의 시간

XP 곡선을 3배로 늘려 잡았다(Lv13 강철도끼까지 하루 90스윙 기준 약 30게임일 = 실시간 5시간).

## Q-v3-4. 노드 총량과 '무한 자원' 방지

스윙 획득이 레벨·도구로 최대 7.8배까지 커지므로, 노드 잔량 감소도 `drain × 배수^0.85` 로 함께 커지게 했다.
즉 **좋은 도구는 같은 나무에서 조금 더 얻고 훨씬 빨리 얻는다**. 장기 채집 상한은 노드 재생(숲 5/일, 바위 3/일)이 쥔다.
**결정 필요**: 후반(티어 5+)에 영토가 넓어지면 노드 수가 늘어 자원이 남아돈다 — 소비처(기념비·화포·상급 업그레이드)를
더 둘 것인가, 아니면 재생률을 티어에 반비례시킬 것인가.

## Q-v3-6. 유물·어전 회의의 티어 게이트

## Q-v3-7. 멀티에서의 스윙 부하

## Q-qa-3. 시뮬 체크포인트의 시드 민감도 — ★ 기준 재정의 필요

`npm run simulate` 은 **seed 42 고정**이다. 다른 씨앗으로 돌리면 결과가 꽤 흔들린다.

| 씨앗 | 티어3 중앙값 | 웨이브5 생존율 | 성녀 격차 | 판정 |
|---|---|---|---|---|
| 42 (기본) | 26일 | 80.0% | 30.0%p | **4/4** |
| 7 | 26일 | 75.0% | 30.0%p | **4/4** |

## Q-qa-4. 걸음이 탐색이 아니라 직진이다

빈 땅을 눌러 걸어갈 때 아바타는 **목적지 방향으로 직진**하고, 막히면 x축·y축으로 한 번씩만 미끄러진다(A\* 같은 길찾기가 없다).
그래서 물가나 바위가 앞을 막으면 **제자리에 선다**. 실브라우저 스모크에서 이 때문에 "나무 곁까지 걸어갔다"가 간헐 실패했다
(스모크는 걸을 수 있는 자리를 골라 누르도록 고쳤다 — 게임 자체는 그대로다).
- 지금은 W A S D 로 돌아가면 되고, 짧은 거리에서는 잘 동작한다.
- **결정 필요**: 상용 기준으로 길찾기를 넣을 것인가(128×128 타일이면 A\* + 경로 캐시로 충분하다). 우선순위 판단 필요.

## Q-qa-5. 안개 즉시 공개의 구조적 한계 — 청크 스탬프가 '게임일' 단위다

`lordMove` 가 그 자리에서 시야를 찍고 `worldDiff{reveal:true}` 를 흘리도록 고쳤다(이번 수정 1번).
다만 청크 스탬프(`fog.chunkStamp`)는 **게임일** 단위라, 같은 날 안에 두 번 밝아진 것을 `sinceTick` 으로 가려낼 수 없다.
그래서 즉시 공개분은 스탬프 함수가 돌려준 **청크 목록을 직접 들고** 만든다(정상 동작하지만 경로가 둘이다).
- **결정 필요**: 청크 스탬프를 단조 증가 시퀀스(`fogSeq`)로 바꿔 경로를 하나로 합칠 것인가.
  지금 구조로도 새는 곳은 없다(회귀 테스트 `test/fog.test.js` 5건 · `test/e2e.mjs` 안개편이 지킨다). 리팩터링 가치 판단만 남았다.
- 성능 메모: 즉시 스탬프는 **새로 밝아진 칸이 하나라도 있을 때만** 마스크를 다시 만든다.
  같은 칸을 다시 보고하거나 이미 본 땅을 오가면 비용이 0 이다 — 비용이 '메시지 수'가 아니라 '새로 알게 된 정보량'에 붙는다.

## Q-qa-6. 실시간 ack 가 창고 잔고를 싣는다 (대역폭 vs 즉시성)

실시간 명령(`actionSwing`·`combatSwing`)의 ack 에 **그 순간의 창고 잔고**(`resources`, 7개 숫자)를 싣게 했다.
- 이유: 실시간 명령은 `state`(NationView 전량)를 다시 빚지 않는데, 그러면 **도끼질을 해도 화면의 자원칸이 최대 10분 묵는다**.
  (예전에는 아바타가 걸을 때마다 `lordMove` 가 상태 전량 방송을 일으켜 우연히 가려져 있었다 — 걸음을 멈추면 드러났을 사고다.)
- 지금은 ack·`swing` 중계에 실린 **권위값**을 화면 장부에 그대로 옮겨 적는다(예측이 아니라 서버 값이라 어긋나지 않는다).
- 같은 이유로 **재배 상태**(`readyAt`·`harvestReady`·`stage`)도 ack 에 싣는다. 이게 없던 동안
  화면은 **거둬 버린 빈 밭을 계속 두드렸다**(서버는 `NOT_READY` 로 튕기고 화면은 다음 일 틱까지 그 사실을 몰랐다).
  실패한 ack(`NOT_READY`)도 `{nodeId, readyAt, harvestReady:false}` 를 실어 준다.
- **확인 필요**: 5인 동시 접속에서 초당 최대 10회 × 십여 개 숫자면 무시할 양이지만, Q-v3-7 의 실측과 함께 확인해 달라.
- **원칙으로 못 박을 것**: 실시간 명령이 바꾸는 상태는 **빠짐없이 ack 에 실어야 한다**.
  하나라도 빠지면 그 값은 최대 10분 묵는다 — 위 두 건이 모두 그렇게 새어 나온 것이다.

## Q-qa-8. 성능 지표의 정의를 바꿨다

기존 스모크는 「평균 프레임 시간 < 16ms」를 봤는데, 이 값은 **프레임 간격**이라 60fps 로 맞물려 돌면 늘 16.67ms 다 —
**절대 통과할 수 없는 조건**이었다. 두 가지로 나눠 다시 정의했다.
- **한 프레임을 그리는 데 든 시간** < 16ms (실측 **0.27~0.28ms**, 95번째 0.40ms) ← 이게 진짜 성능 값이다
- **프레임 간격 95번째** < 22ms (끊김 판정, 실측 16.7ms)
- **확인 필요**: 헤드리스 크롬(소프트웨어 렌더)에서 잰 값이다. 실기(GPU) · 저사양 노트북 · 주민 60명 + 웨이브 전투 중
  같은 **최악 조건에서의 값**은 아직 없다. 상용 기준이라면 그 측정이 따로 필요하다.

## Q-v31-1. 사슬의 「여는 조건」 해석 — 표대로 못 옮긴 두 칸 (★ 확인 필요)

§11-2 표의 「여는 조건」 열은 **그 장을 여는 조건**과 **그 장의 목표**가 섞여 있다.
구현은 「장 N 의 목표 = 장 N+1 의 여는 조건」으로 읽고, 장마다 **칸(step)** 을 두어 목표 카드를 한 장씩 넘겼다.
표와 다르게 놓인 것은 둘이다.

| 표 | 구현 | 왜 |
|---|---|---|
| 3장 허기 「열매 채집·어로·밭 개간 → 첫 수확 팡파레」 | 3장 = 식량 20 **→ 오두막 완공**(칸 둘) | 4장의 여는 조건이 「오두막 완공」이라 3장 마지막 칸이 오두막이어야 사슬이 이어진다 |
| 5장 「주민 3+곡창 완공」 | **4장** 마지막 칸 = 주민 3 + 곡창, 5장 = 주민 5 → 촌락 승격 | 5장의 클라이맥스가 「촌락 승격(티어 2)」이고 티어 2 조건이 주민 5라 그 둘을 같은 장에 두었다 |

- **결정 필요**: 이 해석이 맞나. 아니면 표대로 3장을 「식량만」으로 끝내고 오두막을 4장 첫 칸으로 옮길까?
  (지금 구현은 하니스·스모크가 **마커만 보고** 1장→6장을 10게임일에 통과한다.)
