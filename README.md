# Regiond

맨손으로 시작해 정착지를 키우는 엔드리스 정착지 성장·타워디펜스 웹게임입니다. 한 정착지를 1~5명이 함께 운영하며, 빈자리는 동료 봇이 채웁니다.

2026.08 · 1인 개발(커밋 기준, NHN 게임 공모전 출품용) · Node.js 22(ESM), Express, Socket.IO, 바닐라 JS Canvas, node:test, jsdom, Python(에셋 파이프라인)

## 왜 만들었나

"텍스트만 있어서 재미없다", "뭘 해야 할지 모르겠다"는 피드백에서 출발했습니다. 스타듀밸리의 손맛(직접 캐고 짓기)과 4X 전략 게임의 정보 구조(역할군 국가 경영)를 섞었습니다. 시간이 지나기만 해서는 아무것도 열리지 않고, 플레이어가 행동해야 게임이 진행되도록 설계했습니다.

## 주요 기능

- 정착지 티어 0~6+: 조건을 채우고 승격하면 영토가 넓어지고, 건물과 UI가 단계별로 열립니다(점진 공개)
- 주민 유입(주거 수용력, 식량 여유, 매력도), 개인 스킬 5종과 스윙 단위 채집, 건물 39종(건물마다 따로 티어를 올림), 울타리 드래그 배치
- 엔드리스 웨이브: 적이 실제로 걸어와 울타리를 두드리고, 터렛·민병·플레이어가 함께 싸웁니다
- 384×384 공유 월드, 안개(fog), 생태계(자원 재생), 이웃 AI 국가와의 교역
- 멀티플레이: 초대 코드로 합류하고 역할(각료)마다 볼 수 있는 정보가 다릅니다. 빈자리는 동료 봇 넷이 실제로 채집·건설·전투를 하다가 사람이 들어오면 자리를 내줍니다
- 사건 문장 표현 계층: `ANTHROPIC_API_KEY`가 있으면 Claude가 문장을 다듬고, 없으면 템플릿으로 대신합니다

## 기술적으로 고민한 것

**1. 서버 권위 + 결정론 시뮬레이션**
- 문제: 멀티플레이 판정이 일관돼야 하고, 밸런스 수치를 바꿨을 때 그 결과가 재현돼야 했습니다.
- 선택: 게임 로직을 서버의 순수 함수 `step()` 파이프라인(`server/engine/`)에 모았습니다. 난수는 시드 기반 mulberry32(`server/engine/rng.js`)만 씁니다. 일 틱(경제), 실시간(스윙·전투), 0.25초 서브틱(전투 시뮬)은 분리했습니다. 모든 수치는 `data/*.json`으로 뺐습니다.
- 결과: 같은 엔진을 무접속 시뮬레이터(`npm run simulate`, 20회 × 85게임일)가 그대로 가져다 씁니다. 그래서 밸런스를 바꿀 때마다 체크포인트 리포트로 확인합니다(예: 웨이브 basePower 520→470 되돌림, `docs/GDD3.md` §17-E).

**2. 정보 비대칭을 서버에서 강제**
- 문제: 역할마다 볼 수 있는 정보가 달라야 하는데, 이를 클라이언트가 숨기면 우회할 수 있습니다.
- 선택: 서버가 역할별 NationView와 월드 스냅샷을 따로 만들어 보냅니다(`server/engine/view.js`). 클라이언트-서버 계약은 `docs/PROTOCOL.md` 하나를 정본으로 삼고, 정적 검사(`npm run check:ui`)가 폐기된 명령을 쓰는지 잡아냅니다.

**3. LLM은 문장만, 수치는 엔진이**
- 선택: 표현 계층(`server/expression/`)은 사실 스냅샷(JSON)만 받아 한두 문장을 돌려줍니다. 수치를 만들지 말라는 규칙을 시스템 프롬프트에 고정했고, 5초 타임아웃이 지나면 템플릿으로 대신합니다.
- 결과: API 키가 없거나 응답이 늦어도 게임 상태에는 영향이 없습니다.

**4. 계층별 자동 검증**
- 단위·E2E 테스트는 `test/`에 60여 개 파일이 있고, README 기준 370개입니다. jsdom 클라이언트 하니스(`npm run harness`)는 목표 카드와 마커만 따라 6장까지 진행합니다. 헤드리스 크롬 스모크(`npm run smoke`)는 실제 마우스 조작과 384맵 프레임 시간(<16ms)을 측정합니다.
- 월드 시드를 `?seed=20260804`로 고정해, 실패 원인이 코드인지 지도인지 가릴 수 있게 했습니다.

## 구조

```
server/
├── index.js           # express + socket.io, 디버그 REST(운영에서는 404)
├── engine/            # 틱 파이프라인: 경제·전투·웨이브·주민·진행 감독·안개·동료 봇 (순수 함수)
├── expression/        # 사건 문장 표현 (템플릿 / Claude 어댑터)
└── sim/               # 무접속 시뮬레이터 (엔진 재사용)
data/                  # 밸런스 다이얼 JSON (buildings, waves, tiers, chapters ...)
public/                # 바닐라 JS 클라이언트 (GM 네임스페이스, 스크립트 56개)
test/                  # node:test 단위 테스트 + e2e.mjs
harness/               # jsdom 하니스, 헤드리스 브라우저 스모크, UI 규칙 검사
tools/pipeline/        # ComfyUI 기반 에셋 생성·후처리·QA 스크립트
docs/                  # GDD3(설계), PROTOCOL(통신 규약), SPEC, UIUX, QA 기록
```

## 실행 방법

```bash
npm install        # Node 22 이상, 빌드 단계 없음
npm start          # http://localhost:3000
```

- 서버 없이 UI만 둘러보려면 `http://localhost:3000/?mock=1`로 엽니다.
- 테스트: `npm test`, `npm run e2e`, `npm run harness`, `npm run smoke`(크롬 필요, `CHROME_PATH`), `npm run check:ui`
- 밸런스 시뮬: `npm run simulate`
- 환경변수: `PORT`, `HOST`, `NODE_ENV`(`production`이면 `/api/debug/*` 잠금), `DEBUG_API`, `SAVES_DIR`, `ANTHROPIC_API_KEY`(선택)
- 배포: `render.yaml`(Render), `railway.json`(Railway), GitHub Pages 클라이언트 워크플로가 있습니다. 자세한 내용은 `docs/DEPLOY*.md`에 있습니다.

## 회고

규칙 엔진은 처음부터 순수 함수로 나눠 두어서 테스트와 시뮬레이션을 붙이기 쉬웠습니다. 반면 렌더링은 에셋을 넣은 뒤에야 메모리 급증(지형 캐시 상한 없음)과 프레임 드랍이 드러났고, 대부분 문제가 생긴 뒤에 대응해야 했습니다. 성능 예산은 에셋을 넣기 전에 먼저 정해야 한다는 것을 배웠습니다.
